# 024 – Windows app

- **Status:** in-progress
- **Priority:** P2
- **Depends on:** 001, 002, and every spec it ports (003–016, 019, 020, 022, 023)

## Goal

Brouk on Windows 10 and 11 (x64) with the same features as on macOS, so the user and colleagues on Windows PCs can use it for work (002).

## Description

The Windows app is the existing portable core (`src/core/`, `src/cef/`, `src/renderer/`), the same internal pages (`web/`), and a new native shell in C++ on the Win32 API in `src/platform/win/` (decided in 001). The shell does what `src/platform/mac/` does on macOS: windows, the tab strip, toolbar and address bar, menus, popups and prompts, and the system integration (secret store, default browser, updates). Features behave as their specs describe; where a spec names a macOS control or shortcut, the Windows app uses the Windows equivalent (Ctrl for ⌘, a "⋮" menu at the right of the toolbar for the menu bar), as Chrome does on Windows.

It is built in stages, each ending with a build the user tests on Windows:

| Stage | Goal | Ports |
|---|---|---|
| **W1 – Browse the web** | One window with tabs, address bar with search, back/forward/reload, standard shortcuts, the 012 basics (dialogs, permissions, sign-ins, errors, find, zoom, print, full screen, downloads), the internal pages open in their windows | 003 (basic), 012, 016 |
| **W2 – Everyday browser** | Profiles side by side, settings with live reload, session restore, bookmarks bar, history, downloads list, task manager, command palette, closed tabs | 003, 004, 005, 011, 013, 014, 015, 020 |
| **W3 – Work features** | Passwords (built-in in Credential Manager, Bitwarden CLI, Windows Hello unlock), autofill, ad blocking with the shield, developer tools dock, link routing with the picker and Brouk as the default browser | 006, 007, 008, 009, 010 |
| **W4 – Release** | Per-user installer, WinSparkle updates from a Windows feed in the releases repo, SignPath signing, built in CI | 019, 023 |

## Acceptance criteria

- [ ] W1–W3: each feature's acceptance criteria hold on Windows 11 x64, except where its spec says the criterion is macOS-only; differences are recorded under Notes in that spec.
- [ ] The Windows app builds in CI on every pull request, and every pull request that changes `src/platform/win/` gives the user a build to test (a zip of the app as a workflow artifact).
- [ ] A smoke test on the Windows CI runner starts the app, loads the test pages and the internal pages, crashes a renderer and quits, like the macOS smoke test (019).
- [ ] User data lives in `%LOCALAPPDATA%\Brouk\` (settings, profiles, Chromium's data), as Chrome keeps its data in `%LOCALAPPDATA%\Google\Chrome\User Data`.
- [ ] Secrets go only to Windows Credential Manager; biometric unlock uses Windows Hello.
- [ ] The app follows the system light/dark mode and accent colour, scales on high-DPI displays (per-monitor DPI awareness v2), and its controls work with the keyboard and a screen reader (UI Automation names).
- [ ] W4: an installer installs per user without admin rights; the app updates itself through WinSparkle with EdDSA-signed updates; the installer and app are signed through SignPath.
- [ ] `src/core/` gains no Windows includes; Windows code reaches the core only through the interfaces in `src/core/` (CLAUDE.md).

## Out of scope

- Windows on ARM (002, deferred).
- Windows Store / MSIX and winget (distribution, 002 deferred).
- Linux as a user-facing platform.

## Configuration

The same settings as on macOS. Settings that only exist on one system are hidden on the other.

## Open questions

None.

## Notes

- 2026-10-29 (user's decisions):
  - **Testing:** the user tests in a Windows 11 x64 virtual machine on the Intel Mac (e.g. VMware Fusion, free for personal use). Claude Code checks each build in CI first (smoke test, screenshots on the Windows runner).
  - **Window frame:** the tab strip fills the title bar, like Chrome and Edge and like Brouk on macOS: a custom frame drawn by Brouk that keeps the system's minimise/maximise/close buttons, snap layouts on the maximise button, Aero Snap and the window menu.
  - **Order:** W1, W2, W3, W4 as in the table above.

- 2026-10-29: data location follows Chrome on Windows (`%LOCALAPPDATA%`, not the roaming `%APPDATA%`): Chromium's data is large and machine-specific, and the settings live with it as on macOS. This answers 004's open Windows location.
- The macOS UI is about 22,000 lines in 86 files (`src/platform/mac/`); the Windows shell is a port of comparable size, so it is split into many pull requests, one or a few features each.
- 2026-10-29 (implementation): Chromium's own profile, behind CEF's global request context (used only for background downloads: ad blocking lists, the breach check), lives in `web/Default`; the first Brouk profile (id `default`) in `web/default`. On Windows, whose file names ignore case, that is one folder: the two profiles locked each other's databases and Chromium showed "Profile error occurred". On Windows Brouk starts Chromium with `--profile-directory=Chromium`, so its profile has a folder of its own. On macOS the two share `web/Default` and have worked so far (macOS file locks do not block within one process); the same switch was tried there and made Chromium fail to open its password databases in a new data folder, so macOS is unchanged. CEF's `CefSettings::cache_path` cannot move that profile (CEF ignores a child folder under the Chrome bootstrap).
- 2026-10-29 (implementation): the Windows app is CEF's sandboxed layout: `brouk.exe` is CEF's prebuilt `bootstrap.exe`, which starts the sandbox and calls `RunWinMain` in `brouk.dll` (all of Brouk, for every process type). The first window has back, forward, reload and the address bar around one tab; links that would open a tab open a window until the tab strip exists. The smoke test (019) runs on the Windows CI runner: the test pages load, a crashed renderer recovers after a reload, and the app quits when its window is closed.
- 2026-10-29 (implementation): tabs in the title bar. Brouk removes the system title bar (`WM_NCCALCSIZE`) and draws the tab strip and the window's minimise, maximise and close buttons itself; it answers `WM_NCHITTEST` with the system's codes, so dragging, double-click to maximise, Aero Snap, the window menu and Windows 11's snap layouts (on the maximise button) work as in other apps. Tab order, the active tab and where new tabs go come from the core's `TabStripModel`, widths from `LayoutTabStrip`, as on macOS. Popups open as tabs next to their opener, or in a popup window (system title bar, read-only address bar) for `window.open()` with a size, as in Chrome. Colours follow the system's light or dark app mode. Not yet: the tab strip is not exposed to screen readers (UI Automation), and there are no tab tooltips or tab context menu.
- 2026-10-29 (user's decision): the commands of the macOS menu bar are in a "⋮" menu at the right of the toolbar, as in Chrome and Edge on Windows (a classic menu bar and shortcuts only were the alternatives). It grows with the ported features; the macOS app is unchanged. First items: New tab, New window, Brouk Help (F1), Open-source licences, Exit.
- 2026-10-29 (implementation): internal pages. The web pages and the licences (023) are built into `<app>\web`; `brouk://` pages load in their own request context, as on macOS; on Windows it keeps its (empty) data in `web\internal`, because an in-memory context made Chromium create its `Default` profile folder again, the folder that collides with the first profile's. The licences open in a tab, help in its own window (016). Pages that need features not yet ported (settings, history, bookmarks, passwords, downloads, profiles) come with those features.
- 2026-10-29 (implementation): dialogs over the page. JavaScript dialogs (alert, confirm, prompt, "leave site?"), "page unresponsive" and "open <app>?" are drawn by Brouk over their tab's page (tab-modal: the page gets no input meanwhile, other tabs stay usable), the permission prompt at the top left of the page, and the crash page ("Aw, Snap!") over a crashed tab, with the texts and buttons of the macOS app (012). Differences from macOS: the page is not dimmed behind a dialog, the default button has the system's accent colour, and the permission prompt does not yet say when Windows' privacy settings block the camera or microphone. Links to other apps open with the app Windows has registered for the scheme (`ShellExecute`), escaped as Chrome does; schemes without an app do nothing.
- 2026-10-29 (implementation): find in page and zoom. Each tab has its own find bar at the top right of its page (Chrome on Windows): Ctrl+F, F3/Ctrl+G and Shift+F3/Ctrl+Shift+G, Enter/Shift+Enter in the field, Escape to close. Typing searches as Chrome does, with the first match current ("1/6"). Zoom with Ctrl+Plus/Minus/0 and the "⋮" menu; a "125 %" indicator at the right of the address bar resets the zoom when clicked. Not yet: zooming with Ctrl+mouse wheel does not update the indicator until the tab changes. The smoke test checks both with real key presses (keys sent through the DevTools protocol do not reach Brouk's shortcuts).
- 2026-10-29 (implementation): print and full screen. Ctrl+P and "Print…" in the "⋮" menu open the system's print dialog (Alloy style has no print preview). A page's HTML full screen and F11 make the window cover its monitor without frame, tab strip or toolbar, with Chrome's "Press Esc/F11 to exit full screen" hint. Switching tabs, Escape or closing the tab ends a page's full screen. When the window is activated again, the focus goes back to where it was (address bar, find bar, a dialog over the page, or the page), as in Chrome.
- 2026-10-30 (user's decision): screen reader support (UI Automation for the custom-drawn tab strip) is postponed; Brouk's own features come first, starting W2 with profiles (005). The acceptance criterion on keyboard and screen reader use stays; it is done before W4.
- 2026-10-30 (implementation): HTTP sign-in needs no Brouk code on Windows either: Chromium shows its own "Sign in" dialog (Chrome bootstrap, as on macOS). The address bar shows "Pop-ups blocked" with a menu to open a blocked popup or allow pop-ups for the site. Screen sharing uses Brouk's own picker over the tab (screens, then up to 12 windows by title, no thumbnails): Windows has no system picker that names Chromium's sources; screens are numbered as WebRTC numbers display devices. Right-click on a tab shows Chrome's tab menu (new tab to the right, reload, duplicate, pin, mute site, close / others / left / right); tabs show their title as a tooltip. Not yet: a muted tab shows no icon. Downloads ask where to save each file in W1 (Chromium's "Save As" dialog); saving to the Downloads folder without asking comes in W2 with the downloads button and list (014), which need the history database (013).
- 2026-10-30 (implementation): profiles (005), first part. Each tab belongs to a profile and uses that profile's web data (one request context per profile, as on macOS). The tab strip shows each profile's group: a chip in the profile's colour with its name and number of tabs (click: collapse or expand), its tabs with a coloured line under them, and its own "+"; the default profile's group is always there. Links, popups and duplicated tabs stay in their tab's profile; `--profile` opens a profile from the command line. The profile manager (`brouk://profiles`) opens in its own window, also at startup if chosen; "⋮" → Profiles opens a new tab in a profile or the manager. Deleting a profile asks first (a system message box), closes its tabs and removes its web data at the next start. The profile colours are in the core now (`profile_colors`); the macOS app still has its own copy. Not yet on Windows: dragging a tab to another profile, export and import, the profile picker of link routing (W3).
- 2026-10-30 (implementation): profile export and import on Windows, with the system's Save and Open dialogs (`file_dialogs`; the Save dialog says what the file contains). Until bookmarks (011) and passwords (008) come to Windows, an export has the profile's name, colour and settings only, and an import skips the bookmarks and passwords of a file from macOS and says so. Writing the file goes through a temporary file (`core/text_file`), and files over 16 MB are refused before they are read.
- 2026-10-30 (implementation): moving a tab to another profile (005) on Windows: dragging a tab over another profile's group highlights that group's label; dropping it there asks in a panel over the page ("Move" / "Cancel", as on macOS), then opens the tab's address in that profile and closes the old tab. The question is tab-modal like the other panels, so other tabs stay usable.
- 2026-10-30 (implementation): settings (004) on Windows. `brouk://settings` opens in its own window ("⋮" → Settings), as on macOS. Live reload: a thread waits for `ReadDirectoryChangesW` on the data folder and re-reads the settings 0.3 s after a settings, request rules or link routing file changes. Which files count is shared core code (`IsLiveReloadedFile`), and Chromium's `web\` folder is ignored. Settings that already apply on Windows: the theme (`appearance.theme`, for Brouk's window parts and for web pages: a request context's colour scheme does not reach Alloy-style browsers' `prefers-color-scheme` on Windows, where Chromium follows the system's app mode, so each browser gets the choice through DevTools emulation, `Emulation.setEmulatedMedia`) and the JSON viewer; the search engine was already read on use. Export and import of settings use the Save and Open dialogs. "Show the settings file" opens File Explorer with `settings.yaml` selected. Panels for features not yet on Windows (ad blocking, autofill, link routing, default browser) report that they come later.
- 2026-10-31 (implementation): session restore (015) on Windows, with the same `session.yaml` and startup decision as macOS. Only the active tab of each window loads; the others show their saved title and get their browser when first shown (a restored tab never shown closes at once). The frame is saved as Windows' normal position (workspace coordinates, like `GetWindowPlacement`) with a new `maximized` flag in the session, and ignored when it is on no monitor any more. As Brouk on Windows quits with its last window (Chrome), the session is taken when the last normal window starts closing (its title bar's close button, Alt+F4, or "⋮" → Exit) and saved with `clean_exit: true` at quit; closing the last tab instead leaves nothing to restore, as the user closed it. If a page then cancels the close ("Leave site?" → Stay), saving resumes with the next window that opens. After a crash with "Open a new tab", the "Restore pages?" panel appears over the new tab (Chrome shows it as a bubble at the top right). The smoke test quits, checks the saved session, starts again and checks that the last window comes back with only its active tab loaded.
